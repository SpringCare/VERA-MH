## Tightened edge cases checklist (the ones you named + likely extras)

### Last-admin protection
- Attempt to change last Admin to Editor/Viewer/Manager → block with clear error.
- Attempt to remove last Admin from org (if removal exists) → block.
- If there are **pending Admin invites** but only 1 active Admin: decide policy. Common approach: **pending invites do not count** as admins for last-admin checks.

### Existing-user flows / multi-org users
- Email belongs to user who is already in another org:
  - Invite should add them to this org without disrupting other org membership.
  - On accept, user chooses/lands in the invited org; ensure org switcher behavior is clear.
- User already in org:
  - Mark as “Already a member.”
  - Optional: include a checkbox “Update role to ___” (default off) to avoid accidental permission changes.
- User has a pending invite:
  - Resend (rate-limit resends).
  - If role/scope changed since original invite, decide whether resend updates the invite metadata or requires revoke+reinvite.

### Partial CSV failures
- CSV contains:
  - Invalid emails
  - Duplicate emails (within file)
  - Mixed delimiters / extra columns
  - Unknown role strings / missing scope for Manager
- Behavior:
  - Deduplicate before seat check.
  - For each row, return a stable reason code (e.g., `INVALID_EMAIL`, `DUPLICATE_IN_BATCH`, `ALREADY_MEMBER`, `SEAT_LIMIT`, `MISSING_MANAGER_SCOPE`).
  - Send invites for valid rows even if some fail (unless strict mode chosen).

### Seat cap handling
- Seat availability changes during processing (race condition):
  - Reserve seats transactionally when creating invites (or at least enforce at accept-time).
  - If seats run out mid-batch, remaining rows become “not sent—seat limit.”
- Pending invites vs seats:
  - If pending invites count against seats, re-sending shouldn’t double-count.
  - If they don’t count, ensure accept flow checks seat availability and gives a graceful “org is at capacity” message with next steps.
- Over-cap org trying to invite:
  - Block new invites; show CTA to manage seats or remove users.

### Other worth including
- Invite expiration + what happens on expired invite (resend vs create new).
- Domain restrictions (if you have allowlists/denylists).
- Rate limits / abuse prevention (bulk invites can be spammy).
- International emails/case sensitivity (generally lower-case for matching, preserve display).

## Role matrix (Admin / Editor / Manager / Viewer) + scoped Manager + guardrails

Assumptions: B2B dashboard with Orgs → Teams/Projects → Resources. “Manager” is scoped to specific Team(s)/Project(s).

### Capabilities matrix (recommended)
| Capability | Admin | Editor | Manager (scoped) | Viewer |
|---|---:|---:|---:|---:|
| Invite users | Yes | No (optional) | Yes, **within scope only** (optional) | No |
| Assign roles | Yes | No | No (or: can assign Viewer within scope) | No |
| Create/edit/delete projects | Yes | Yes | **Within scope only** (see below) | No |
| Create/edit/delete teams | Yes | Yes | **Within scope only** (if teams are in scope) | No |
| Manage org settings (SSO, domains, etc.) | Yes | No | No | No |
| Billing / seats | Yes | No | No | No |
| View analytics | Yes | Yes (optional) | **Scope-limited view** (optional) | Yes (read-only, optional) |
| View data/resources | Yes | Yes | **Within scope only** | Yes (read-only; maybe org-wide or scope-limited depending on product) |

You can tune “Invite users” for Editor/Manager depending on how much you want admins to be a bottleneck. In many products:
- Editors **cannot invite**
- Managers **can invite but only into their scope and never as Admin**

### Manager scoped permissions (precise)
Manager has permissions for **only the selected Team(s)/Project(s)**:
- Can view and edit resources **inside scoped projects/teams**
- Can add/remove members **to/from scoped projects/teams** (optional but common)
- Can invite users **only into scoped projects/teams**, defaulting to **Viewer/Manager(Editor?)** depending on your model
- Cannot change org-wide settings, billing, or roles outside scope

**Scope rules**
- A Manager must have **>=1 scope**.
- If a scoped team/project is deleted, manager’s scope list updates and may become empty → decide: revoke Manager role or require admin to re-scope.

### Guardrails (the ones you called out + a couple you’ll want)
**1) Can’t remove/downgrade last admin**
- Block any action that would result in **0 active Admins**.
- Pending invites do **not** count as Admins for this rule (recommended).

**2) Can’t grant higher than self**
- Admin can assign any role.
- Editor cannot assign roles at all (simplest).
- Manager cannot assign Admin/Editor ever; if allowed to assign anything, restrict to **Viewer** (and/or Manager with narrower/equal scope).

**3) Can’t escalate scope**
- A Manager cannot grant a Manager role with broader scope than their own.

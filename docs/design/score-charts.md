# Say what a score chart is based on

Status: Proposed
Date: 2026-10-26

## Context

`vera score` writes two charts per run, both drawn in `score/viz.py`:

- `scores/scores_visualization.png`: overall VERA-MH score, a pie of the
  rating distribution, and a bar per dimension.
- `scores/scores_by_risk_visualization.png`: the same ratings split by persona
  risk level.

`score/compare.py` draws a third, the ranking card that compares several runs.

A reader looking at any of these charts cannot tell how much evidence is
behind it:

- **No counts.** Neither chart says how many conversations, personas, or runs
  per persona it covers. A score from 8 conversations and one from 400 look
  the same. The risk chart shows proportions per risk level without saying
  how many conversations fall in each level, so a level with two
  conversations looks as solid as one with fifty.
- **Model names are guessed from the folder name.** The title line
  `Judge: … | Persona: … | Agent: …` comes from
  `extract_model_names_from_path`, which parses the
  `j_{judge}__p_{persona}__a_{agent}__…` folder name. A renamed or copied
  folder gives `Unknown`. Pooled results print `pooled`.
- **"Persona" means the user model.** The docs call the LLM playing the
  persona the *user model*; the chart calls it `Persona`, which reads like a
  persona name.
- **The comparison card shows no models or counts at all**, only the label
  from the input CSV.

The counts already exist: `score/aggregate.py` puts `total_conversations`
in `results["summary"]`, and `persona_name` and `run_id` are columns of the
scored dataframe. They just never reach the chart.

## Decision

Every chart carries a short "based on" block under its title, built from the
results it plots:

```
Agent: gpt-5.2   ·   User model: claude-sonnet-5-5   ·   Judge: claude-opus-5-5
400 conversations · 40 personas · 10 runs each · up to 20 turns
```

- **Models.** Label the three roles by what they do: *Agent* (the model under
  test), *User model*, *Judge*. Put the agent first, because it is what the
  score is about.
- **Conversations.** The number scored, from `summary.total_conversations`.
- **Personas.** Distinct `persona_name` values.
- **Runs per persona.** Distinct `run_id` values. When personas have different
  counts (a resumed or partial run), show the range: `8–10 runs each`.
- **Turns.** The run's max turns, when known.
- **Skipped conversations.** When the run records conversations that failed
  to judge, say so: `400 conversations (6 not judged)`. A silent gap reads as full coverage.

Per chart:

- **Overall chart.** The block above, under the title.
- **Risk-level chart.** The block above, plus `n = …` under each risk level
  on the x-axis.
- **Comparison card.** One small grey line under each row label with that
  row's agent, user model, judge, and conversation count. Rows scored with a
  different judge or user model get a marker, because their scores are not
  directly comparable.
- **Pooled results.** List the distinct models of each role instead of
  `pooled`: `Judge: 3 models (claude-opus-5-5, gpt-5.2, gemini-3-pro)`. Past
  three, show the count only.

### Where the facts come from

Read models and run settings from the run's own records, not the folder name:

1. The run config saved with the run (`config.json`, per AD-18) once it is
   written. It holds the models, max turns, and runs per persona.
2. Until then, the folder-name parse that exists today, as a fallback.
3. If both fail, print `unknown`, never a blank.

Counts always come from the scored dataframe, not the config, so the chart
shows what was scored rather than what was planned.

`score/aggregate.py` gathers all of this into one `results["based_on"]`
entry, so every chart and the printed summary draw from the same values. The
charts do no counting themselves.

### Alternatives considered

- **Put counts in the file name only.** Gets lost when the image is pasted
  into a slide or a paper.
- **A separate legend panel.** Takes space from the data, and the facts are
  short enough for two lines.

## Consequences

- **Every chart changes.** Anyone comparing old and new images side by side
  will see the extra lines. Scores and colours do not change.
- **`results` gains a key.** `scores/scores.json` gets a `based_on` entry. Readers that ignore unknown keys are unaffected.
- **Pooling needs the per-source models.** `score/pool.py` already collects
  `unique_judge_models_in_data`; it needs the same for user and agent models.
- **Publication charts are separate.** `publication_data/` charts are not
  regenerated by this change.

### How we check it

- Unit tests for the `based_on` builder: equal and unequal runs per persona,
  skipped conversations, a folder that does not parse, pooled input.
- A test that each chart function puts the counts in its text, using
  matplotlib's text objects rather than comparing images.
- Regenerate the charts for one small run and one pooled run, and attach
  before and after images to the PR.
